# Данные и жизненный цикл дашборда

`js/dk-dashboard.js` — независимый от DOM и фреймворка контракт данных и
контроллер загрузки. Его API доступно как `window.dkDashboard`; версия
контракта данных — `schemaVersion: 1`, версия API — `1.0.0`.
Это начальная реализация для эталона, а не заявление о готовности любого
источника или приложения к production.

## Где выполняются расчёты

| Режим | Источник | Что приходит в браузер |
|---|---|---|
| `local` | Небольшой полный набор наблюдений | Все строки; фильтрация, итоги и пагинация выполняются локально |
| `server` | API для больших наборов | Одна страница строк, итоги и дневные серии для всего выбранного среза |

Для десятков тысяч строк используйте `server`. KPI и график относятся ко
всему срезу, таблица — к его текущей странице. Переключение страницы не
меняет итоги. Локальный режим не является механизмом выгрузки больших баз.

## Запрос

```js
{
  filters: { service: ['Водоснабжение'] },
  period: { from: '2026-10-01', to: '2026-10-21' },
  page: 1,
  pageSize: 20
}
```

- `filters` по умолчанию `{}`. Значения одного измерения объединяются по
  «ИЛИ», разные измерения — по «И». Пустой массив означает «все значения».
- Неизвестное значение фильтра даёт пустой срез. Неизвестный идентификатор
  измерения — ошибка запроса. Строки сравниваются точно, с учётом регистра.
- `period` по умолчанию `null`: весь период источника. Границы включаются,
  формат — реальная календарная дата `YYYY-MM-DD`.
- `page` — положительное безопасное целое, по умолчанию `1`.
- `pageSize` — целое от `1` до `100`, по умолчанию `20`.
- При изменении фильтра или периода приложение сбрасывает `page` в `1`.
- Сортировка пока не входит в контракт. Неизвестные поля отклоняются.
- Нормализация удаляет повторы значений фильтра и сортирует ключи/значения.
  Она не изменяет исходный объект приложения.

## Локальный набор наблюдений

```js
{
  schemaVersion: 1,
  source: {
    id: 'operations-demo',
    label: 'Демонстрационные обращения',
    kind: 'demo',
    updatedAt: '2026-10-21T09:30:00Z'
  },
  period: { from: '2026-10-01', to: '2026-10-21' },
  dimensions: [{ id: 'service', label: 'Услуга' }],
  metrics: [{
    id: 'requests', label: 'Обращения', unit: 'шт.',
    aggregation: 'sum',
    description: 'Число поступивших обращений за дату наблюдения.'
  }],
  rows: [{
    id: 'water-2026-10-01', label: 'Водоснабжение · 1 октября',
    date: '2026-10-01',
    dimensions: { service: 'Водоснабжение' },
    values: { requests: 10 }
  }]
}
```

`source.kind` — `demo` или `live`. `updatedAt` — ISO timestamp с часовым
поясом. Дата загрузки не заменяет дату актуальности источника. Интерфейс
обязан показывать источник, период, единицы и признак демонстрационных данных.
Статус `live` заявляет поставщик; сам валидатор происхождение данных не доказывает.

Каждое измерение и метрика имеют уникальный идентификатор вида
`^[a-z][a-z0-9_-]*$` (регистр допускается); опасные имена объектов запрещены.
У каждой строки уникальный `id`, непустой `label`, дата внутри периода,
все объявленные измерения и значения всех объявленных метрик.
Измерения — непустые строки. Значения — конечные числа или `null`.
Неизвестные поля, дубликаты, строки вместо чисел, пропущенные значения,
неверные даты и неподдерживаемая версия отклоняются.

Строки должны описывать непересекающиеся наблюдения. Ответственность
источника — не включать один объект несколько раз под разными ID и не
смешивать накопительные срезы с дневными значениями. Валидатор проверяет
структуру и внутреннюю согласованность, а не корректность бизнес-формулы.

Агрегации:

- `sum` — сумма известных значений. Допустима только для аддитивных метрик.
- `mean` — невзвешенное среднее известных наблюдений. Не используйте его
  для среднего из предварительно рассчитанных средних с разными весами.
- Доли, проценты, distinct-count и другие формулы не вычисляются автоматически.
  Для них нужно расширить контракт и проверки; нельзя маскировать такую
  метрику под `sum` или `mean`.

## Серверный ответ

```js
{
  schemaVersion: 1,
  mode: 'server',
  query: { filters: {}, period: null, page: 1, pageSize: 20 },
  source: { /* те же обязательные поля источника */ },
  period: { from: '2026-10-01', to: '2026-10-21' },
  dimensions: [ /* определения */ ],
  metrics: [ /* определения */ ],
  rows: [ /* только текущая страница */ ],
  rowCount: 50000,
  totals: {
    requests: { value: 50000, observed: 50000, total: 50000, partial: false }
  },
  series: [{
    date: '2026-10-01',
    values: { requests: 2400 },
    coverage: { requests: { observed: 2400, total: 2400 } }
  } /* остальные даты всего среза */]
}
```

Пример выше показывает структуру, а не самостоятельный согласованный ответ.
API обязано вернуть все объявленные метрики в `totals`, `values` и `coverage`.
`query` — обязательное эхо нормализованного запроса. Если запрошен конкретный
период, `response.period` должен совпадать с ним; при `period:null` сервер
возвращает фактический период источника.

`rowCount` — число всех совпадений до пагинации. Число `rows` должно точно
соответствовать странице. Для страницы за пределами выборки допустимы
`rows:[]` и положительный `rowCount`; состояние остаётся `ready`, чтобы
приложение могло предложить первую страницу.

`series` — дневные агрегаты всего среза, максимум 366 точек, даты уникальны
и возрастают. У всех метрик точки одинаковый `coverage.total` — число
наблюдений за эту дату. Сумма покрытия точек равна `rowCount`; `observed`
суммируется в глобальное покрытие. Значения `sum` складываются, `mean`
взвешиваются по `observed`. Их результат должен совпасть с `totals`.
Для длинных рядов нужен меньший период или отдельное расширение временного
шага; тихо обрезать серию до первых 366 дней нельзя.

Валидатор дополнительно проверяет, что даты и покрытие текущей страницы
входят в полные серии. Если день полностью представлен на странице,
значения таблицы сверяются с соответствующей точкой серии. Невидимые
строки остаются ответственностью сервера.

## Ноль, отсутствие данных и частичное покрытие

Каждый итог имеет `{value, observed, total, partial}`:

- `0` — известное нулевое значение; оно участвует в расчёте.
- `null` — нет наблюдаемого значения; оно не превращается в ноль.
- `observed` — число известных значений, `total` — число строк среза.
- `partial` равно `observed < total`. Покажите рядом «По 8 из 10 наблюдений».
- Если нет известных значений, `value:null`. При пустом срезе `total:0`,
  `observed:0`, `partial:false`, `series:[]`.

Дневные точки содержат такое же покрытие без вычисляемого поля `partial`.
Пропущенная дата не означает ноль: источник должен явно вернуть нулевые
наблюдения, если это подтверждённый результат.

## API

| Метод | Результат |
|---|---|
| `validate(snapshot)` | Копия локального набора с глубокой заморозкой; при ошибке бросает исключение с `code` |
| `select(snapshot, query)` | Отфильтрованное представление; итоги и серии до пагинации |
| `validateResponse(response, query)` | Проверенное серверное представление; итоги не пересчитываются по странице |
| `fetchSource(url, options)` | Функция `load({query,signal})` для HTTP; GET в `local`, POST JSON-запроса в `server` |
| `createSession({load, mode, timeoutMs})` | Контроллер загрузки; `mode` по умолчанию `local`, таймаут 30 секунд |

Представление имеет поля `source`, `period`, `dimensions`, `metrics`,
`rows`, `rowCount`, `totals`, `series`, `query`. Все вложенные объекты
заморожены; данные вызывающего кода не замораживаются и не изменяются.

`fetchSource` принимает `{mode:'server', maxBytes:1048576}`. Размер ответа
по умолчанию ограничен 1 MiB; реальный поток читается с подсчётом байтов и
отменяется при превышении. Одна только заявленная длина ответа не считается
достаточной проверкой. URL, авторизация и доступ к данным задаются приложением.
Для нестандартного протокола передайте собственный `load` с поддержкой signal.

## Подключение жизненного цикла

```js
var session = dkDashboard.createSession({
  mode: 'server',
  load: dkDashboard.fetchSource('/api/dashboard', { mode: 'server' })
});
var unsubscribe = session.subscribe(function (state) {
  // В loading/error view === null: очистить прежние KPI/график/таблицу.
  // В ready/empty отрисовать все блоки из одного state.view.
  renderDashboard(state);
});
session.load({ filters: {}, period: null, page: 1, pageSize: 20 });

// При удалении экрана, включая unmount React/Vue:
unsubscribe();
session.destroy();
// Также вызвать destroy() собственных экземпляров графика и других компонентов.
```

`load(query)` заменяет запрос целиком. `retry()` повторяет текущий запрос.
`getSnapshot()` возвращает состояние. `subscribe(fn)` сразу вызывает
подписчика и возвращает функцию отписки. `destroy()` идемпотентен, отменяет
загрузку, сообщает `destroyed` и отключает подписчиков. Новый экран создаёт
новую сессию. Вызов load/retry после destroy не запускает работу.

Состояния: `idle`, `loading`, `ready`, `empty`, `error`, `destroyed`.
Объект состояния: `{status, query, view, error}`. `error` имеет безопасные
поля `{code,message}`; тело ответа сервера и случайный текст исключения
не передаются пользователю.

Последний запрос побеждает: запоздалые успехи и ошибки не меняют экран,
даже если загрузчик игнорирует AbortSignal. Таймаут также завершает
операцию независимо от поддержки abort. Promise load/retry возвращает
состояние или `null` при вытеснении/удалении сессии.
Неверная форма запроса не передаётся загрузчику; для retry сохраняется
последний синтаксически корректный запрос.

Сессия отвечает за чтение. Создание задач и другие записи должны идти через
отдельный серверный endpoint с проверкой прав и защитой от повторного действия;
после подтверждённой записи приложение повторяет чтение актуального среза.

## Проверки и границы

`node tools/check-dashboard-data.mjs` проверяет контракт, расчёты, покрытие,
страницы, ответ на 50 000 совпадений с ограниченным числом строк, гонки,
таймаут, повтор, уничтожение, неизменяемость, HTTP и лимит потока.
Эти Node-only проверки не подтверждают визуальную доступность, поведение
реального браузера, производительность базы и права реального пользователя.

До подключения production API дополнительно подтвердить формулы, гранулярность,
полноту источника, стабильный порядок серверной пагинации, доступ и стоимость
запросов. Серверный снимок должен быть согласованным: строки, итоги и серии
считаются по одной версии данных, а не тремя несвязанными запросами.
