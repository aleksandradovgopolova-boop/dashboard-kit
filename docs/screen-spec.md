# Статическая сборка screen-spec/1

`tools/build-screen.py` проверяет описание экрана и собирает автономный HTML
из текущего кита. Внутри нет запуска Claude/Codex, React или новой runtime-зависимости.
Python стандартной библиотеки и уже используемый Node.js 22+ нужны при сборке;
готовой странице нужен обычный HTTP-сервер.

Первая поддерживаемая композиция — `plan-fact`, `kind:overview`, полный локальный
набор до 1000 дневных наблюдений. Другие рецепты, серверные страницы и производные
временные ряды не выдаются за реализованные возможности.

## Запуск

```sh
python3 tools/build-screen.py examples/spec/plan-fact.json
python3 tools/build-screen.py examples/spec/plan-fact.json --out /tmp/plan-fact
python3 -m http.server 8780 --directory /tmp/plan-fact
```

Первая команда только проверяет вход, вторая создаёт новую директорию.
Существующий каталог, даже пустой, не перезаписывается. Результат содержит
`index.html`, полный закреплённый SDK в `kit/` и `screen-input.json` с фактически
использованными нормализованными данными. Для нового результата выберите другой
каталог; файлы потребителя и его lock не меняются.

Свой checkout проверяется относительно `kit-release.json` до выполнения его кода.
Для установленного пакета обязательны `--kit PATH --expect sha256:...`: pin берётся
из внешнего lock потребителя. Внешний SDK сначала проходит полную проверку
пакета/контрольных сумм, затем его API используется для валидации данных.
Самозаявленного digest внутри незнакомого пакета недостаточно.

## Описание экрана

Полный исполнимый пример — `examples/spec/plan-fact.json`.

| Поле | Реализованный контракт |
|---|---|
| `schemaVersion` | 1; неизвестная версия отклоняется |
| `id`, `title`, `question` | Идентификатор, название и полезный вопрос пользователя |
| `recipe`, `kind` | plan-fact / overview |
| `source` | Относительные file/registry, grain и полный expectedRows |
| `bindings` | Именованные ссылки на source/named метрику или alias другого binding |
| `filters` | Зарегистрированные select с общей областью действия |
| `widgets` | Tile сначала, затем chart/table; состав задаётся spec, пустые слоты не добавляются |
| `actions` | clear-filters или open-details для конкретной таблицы |
| `responsive` | desktop:balanced, mobile:stack; иных вариантов пока нет |

Привязка `kind:source, field:issued` использует исходную v1-метрику.
`kind:named, field:rate` использует одно определение из registry, включая
формулу/формат/единицу. Идентификаторы bindings образуют своё пространство имён:
raw rate и named rate не смешиваются неявно. Alias имеет `ref`, а не новую формулу;
циклы и неизвестные ссылки отклоняются. Свободных выражений и функций нет.

Поля каждого виджета/фильтра проверяются тем же сгенерированным контрактом,
который доступен через `kit.py schema`, `kit.py validate` и read-only MCP.
[Краткий справочник параметров](../skill/dashboard-build/references/component-parameters.md)
генерируется из одного источника. Это минимальный адаптер screen-spec,
а не обещание поддержки каждого параметра полного JS API.

Chart в v1 использует только исходные дневные серии и одну общую единицу оси.
Несовместимые единицы и named/derived series отклоняются. Для bar/horizontal
используется существующий bar-h. Единица видна в заголовке графика.
Table группирует полный отфильтрованный набор по объявленному измерению;
каждая доля и weighted mean пересчитывается из исходных наблюдений группы,
готовые проценты не складываются. Большая таблица прокручивается внутри виджета.

## Действия и состояния

Один выбранный фильтр меняет КПЭ, график и таблицу вместе. Сброс появляется
только при активном условии и не резервирует место. Подробности открывают
реальную группу из текущей таблицы: те же значения, даты и дневная детализация.
Закрытие возвращает фокус к строке, выбранный срез сохраняется.

Статическая страница ничего не отправляет и не сохраняет на сервере.
Отсутствующие данные, partial, нулевой знаменатель, неполный источник и пустой
результат имеют разные состояния. Известная часть не выдаётся за полный итог.
Краткий статус видим; определение и причина доступны по запросу. Данные/единицы,
период, демонстрационный статус и актуальность источника не скрыты.

Нет лишних постоянных поясняющих абзацев. Вопрос и методика открываются через
«Данные и методика»; график/таблица имеют содержательные названия.
Учебный fixture использует регионы и каналы выдачи, а не смешивает кредиты с ЖКХ.

`dkScreen(root, compiledConfig)` исполняет **нормализованный конфиг компилятора**.
Методы: `setFilters(filters)`, `reset()`, `getSnapshot()`, `destroy()`.
Это не второй произвольный JS-renderer. Для новой версии embedded-данных
пересоберите страницу либо переинициализируйте контроллер; сетевой loader
и неподтверждённая «автоматическая загрузка» здесь не обещаются.

## Безопасность и воспроизводимость

До записи результата отклоняются неизвестные компоненты/параметры/ссылки,
несовместимые типы/единицы/гранулярность, циклы и неразрешённые действия.
Пути данных ограничены input-root; переходы выше него, абсолютные пути
и symlink запрещены. JSON с повторными полями и нечисловыми значениями
NaN/Infinity не принимается.

Порядок подключения берётся из `kit.py head` и dependency closure.
Данные проходят настоящий dkDashboard/dkMetrics, а не второй агрегатор на Python.
Строки в HTML экранируются, JSON защищён от закрытия script-тега; runtime
создаёт DOM текстовыми узлами. Входные строки не становятся JS/HTML.
Встроенные действия ограничены фильтрацией, сортировкой, деталями и легендой.

Одинаковые эффективные входы и версия кита дают одинаковые байты файлов.
Комментарий inputs содержит SHA-256 нормализованного spec и фактически
встроенных данных/определений. Изменение значимых входов видно в diff;
время запуска и случайные output-пути в результат не добавляются.

Проверки: `python3 tools/check-screen-spec.py` (positive/negative, XSS,
standalone/pin, существующий output и воспроизводимость),
`node tools/check-screen-builder.mjs` (настоящий Chrome, числа и действия).
Проверка структуры не заменяет смысловую и визуальную приёмку.
Физические устройства и настоящий скринридер в этих командах не проверяются.

Принципы типизированного каталога/spec исследованы по
[json-render catalog](https://json-render.dev/docs/catalog) и
[custom schema](https://json-render.dev/docs/custom-schema).
Сторонний renderer и его код не переносились.
