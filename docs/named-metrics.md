# Именованные производные метрики

`js/dk-metrics.js` хранит формулу, исходные поля, единицу, формат, направление
и требуемую гранулярность в одном именованном определении. `dkMetrics` v1.0.0,
`registry.schemaVersion:1` — дополнительный контракт к `dkDashboard` v1.
Существующие `sum`, `mean`, HTTP-адаптер и серверные ответы не изменены.

Подключение: `python3 tools/kit.py head named-metrics`. Опись поставит
`dk-dashboard.js` перед `dk-metrics.js`. Фреймворк и вычисление строк через
`eval` не нужны.

## Определение и расчёт

```js
var registry = {
  schemaVersion: 1,
  metrics: [{
    id: 'execution', label: 'Выполнение плана', unit: '%',
    aggregation: 'ratio-of-sums',
    inputs: {numerator: 'issued', denominator: 'plan'},
    scale: 100,
    format: {type: 'percent', digits: 1},
    better: 'increase',
    grain: {time: 'day', dimensions: ['region']}
  }]
};
var result = dkMetrics.select(snapshot, registry, {
  filters: {region: ['Север']}, page: 2, pageSize: 1
}, {
  grain: {time: 'day', dimensions: ['region']},
  coverage: {expectedRows: 4}
});
// result.totals.execution: {value:80, code:'ready', observed:2, total:2, partial:false}
```

`snapshot` — полный локальный набор версии 1 из [контракта данных](dashboard-data.md).
`query` имеет тот же формат и проверку фильтров/периода, что `dkDashboard.select`.
Расчёт идёт по всему выбранному срезу до пагинации: `page` не меняет значение.
Передача результата select, серверного ответа или одной серверной страницы
отклоняется. Серверное объединение достаточных статистик в этой версии не
реализовано; готовые проценты нельзя выдавать за исходные суммы.

У каждого определения обязательны `id`, `label`, `unit`, `aggregation`,
`inputs`, `format`, `better`, `grain`. `scale` по умолчанию 1, положительное
конечное число. Формат: `number`, `decimal` или `percent`, `digits:0..6`.
Направление: `increase`, `decrease`, `neutral`; само по себе оно не задаёт
порог хорошего результата. Формат и подпись получает компонент из этого
определения; числа в интерфейсе форматируются через `dkFmt`.

| Агрегатор | Исходные поля | Формула после фильтрации |
|---|---|---|
| `ratio-of-sums` | `inputs.numerator`, `inputs.denominator` | Σчислитель / Σзнаменатель × scale |
| `weighted-mean` | `inputs.value`, `inputs.weight` | Σ(значение × вес) / Σвес × scale |

Ссылки ведут только к объявленным исходным полям snapshot, не к другим
производным метрикам. Для ratio оба поля должны быть аддитивными (`sum`),
для weighted — аддитивным должен быть вес. Веса неотрицательны. Значения
метрики и вес относятся к одному наблюдению и одной гранулярности.
Если источник уже хранит `rateWeight = rate × volume`, его нужно использовать
как числитель ratio, а не повторно умножать на volume.

Distinct не поддерживается: подтверждённого сценария с исходными уникальными ID
пока нет. Сумма distinct групп не является distinct общего множества.
Неизвестные поля, версии, агрегаторы, ссылки и неверные типы отклоняются
с `error.code='INVALID_METRIC'`; ошибки исходного snapshot сохраняют коды v1.

## Гранулярность и охват

В первой версии поддерживается только `grain.time:'day'` у определения.
Метаданные источника должны совпасть с требуемой гранулярностью; одинаковый
набор измерений сравнивается без учёта порядка. Каждая комбинация дата ×
измерения должна быть уникальной. Несколько записей одного региона за день
требуют дополнительного измерения записи, а не произвольного усреднения.
Месячный источник не проходит как дневной; для будущей месячной версии также
понадобится проверка полных месяцев источника и запроса.

`options.coverage.expectedRows` — заявленная источником численность всего
snapshot до query и pagination. Не вычисляйте её автоматически из `rows.length`:
тогда пропущенные строки перестанут обнаруживаться. Совпадение численности
проверяет заявление источника, а не доказывает полноту бизнес-популяции.
Число меньше фактического — ошибка. Большее число блокирует все производные
срезы: полноту конкретного фильтра нельзя вывести из неполного источника.

| `code` | Значение |
|---|---|
| `ready` | Вычислено; настоящий нулевой числитель сохраняется как 0 |
| `coverage-unknown` | Полная численность источника не подтверждена |
| `incomplete-source` | Не хватает строк относительно заявления источника |
| `grain-unknown` | Источник не подтвердил гранулярность |
| `incompatible-grain` | Гранулярность источника отличается от определения |
| `ambiguous-grain` | Ключ наблюдения повторяется |
| `empty` | В полном источнике нет строк выбранного среза |
| `partial-input` | У нужного исходного поля есть null |
| `zero-denominator` | Известный знаменатель/сумма весов равен нулю |
| `overflow` | Произведение, сумма или результат вне числового диапазона |

Во всех состояниях кроме `ready` значение `null`. Известная часть не выдаётся
за полный процент. `observed` — число строк с обоими известными операндами,
`total` — число строк выбранного среза; `sourceCoverage` хранит полный охват.
Независимая метрика с известными операндами продолжает вычисляться.
Показывайте краткий статус; определение и причину открывайте по запросу.

`dkMetrics.validate(registry,snapshot)` возвращает проверенную замороженную
копию определений. Результат select также глубоко заморожен; объекты
вызывающего кода не изменяются и не замораживаются.

## Контрольные ответы

Исполнимый набор: `tools/fixtures/named-metrics/source.json` и `registry.json`.
Четыре учебных дневных наблюдения, два региона. Общий факт/план 100/200 = 50%,
взвешенная ставка (6×100 + 4×300 + 8×600 + 0×0)/1000 = 6,6%.
Север: 40/50 = 80%, ставка 4,5%; второй день: 30/80 = 37,5%, ставка 4%.
Пагинация не меняет общий ответ. Отдельный случай с разными базами одобрений
даёт 230/300 = 76,6667%, а не среднее региональных процентов.

`node tools/check-named-metrics.mjs` проверяет эти литеральные ответы,
пересечение фильтров, null, 0, пропуск строки, гранулярность, overflow,
отрицательный вес, несовместимый server input и неизменность старого v1.
Проверка включена в `python3 tools/test.py`; она дополняет существующие
числовые и ипотечные проверки. Штатная модель ипотеки не переписана.

Принцип именованного определения исследован по
[Evidence metrics](https://docs.evidence.dev/core-concepts/metrics).
SQL, сторонний runtime и код Evidence не переносились.
