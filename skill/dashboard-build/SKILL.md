# Сборка дашборда на dashboard-kit

Кит — дизайн-система с машинными проверками. Скилл собирает страницу из
компонентов кита и проверяет её двумя способами: технические проверки и
просмотр по задаче пользователя. Чистый check.py не доказывает понятность
показателей, уместность графиков или готовность экрана.

## 0. Сохраняй чужие правки

Человек мог поправить страницу или кит вне разговора. Неожиданная правка —
намеренная: не перезаписывай её, а спроси.

## 1. Найди кит и прочитай опись

Кит — папка с `kit-manifest.json` (в проекте, рядом с ним или `~/dashboard-kit`).
Не нашёл — спроси путь; не собирай по памяти.

```bash
python3 <кит>/tools/kit.py list            # все части кита, строка на каждую — читать ПЕРВЫМ
python3 <кит>/tools/kit.py show hero car   # только нужные части целиком: когда брать, классы, пример
python3 <кит>/tools/kit.py charts          # виды графиков, когда не брать, что услышит скринридер
python3 <кит>/tools/kit.py find карта      # поиск по описи
```

Читатель предупредит, если опись отстала от кода. Тогда
`python3 <кит>/tools/build-manifest.py` — и заново.

## 2. Задача и смысл данных до разметки

Для нового экрана сначала установи: **кто смотрит, какое решение принимает,
на какие вопросы должен ответить обзор, на каком устройстве и размере**.
Используй ответы из разговора; неизвестное спроси до выбора блоков.
Одно число не назначается главным автоматически. Зафиксируй короткий бриф:
аудитория → решение → вопросы → показатели → устройство. Не переспрашивай
то, что уже известно; состав, графики и обычные детали оформления выбирай сам.

Для сборки по данным прочитай [product-review.md](references/product-review.md).
Проведи разбор аналитиком метрик и проверку дизайнером/редактором через
доступные субагенты; при отсутствии делегирования выполни эти проходы
последовательно и не называй их независимой проверкой. Не делегируй обычную
правку одного блока. Главный агент отвечает за итог и согласованность.

Неизвестная формула или знаменатель — вопрос к источнику, а не повод
придумать определение. Продолжай работу с подтверждёнными показателями;
не строй зависимый вывод до ответа.

Перед сборкой хедеров и оболочек виджетов читать [composition.md](references/composition.md) и `kit.py show page-header widget-header widget`.

Где подключать каркас: [chrome.md](references/chrome.md),
[phone.md](references/phone.md). Выбор блока по структуре данных:
[charts.md](references/charts.md), [data.md](references/data.md).

Основных KPI на обзорном экране — обычно пять (5 ± 2), максимум семь,
включая самостоятельный показатель главной карточки. KPI идут перед
подробными графиками; дополнительные метрики — в деталях.

## Согласование новых правил

Пользователь просит согласовывать компоновку через выбор примеров.
Если решения ещё нет в правилах, покажи 2–3 конкретных варианта, задай
вопрос и запиши ответ в DECISIONS.md и нужный reference. Не выдавай
предложенный вариант за утверждённый и не повторяй уже согласованные вопросы.
Для большого набора решений проводи короткие раунды по 3 вопроса;
визуальные различия показывай на примерах. До ответа не меняй зависимую
компоновку. Справочник index.html отражает принятые решения.

## 3. Собери то, о чём просили

**Просят один блок — делай один блок.** «Добавь график» — это график, а не
экран с главной карточкой, лентой и плитками. Порядок экрана из
[layout.md](references/layout.md) — для просьбы собрать экран целиком. Хочешь
предложить больше — предложи словами, не собирай. (Проверочные задачи 4 и 6:
на просьбу об одном графике исполнитель дважды добавил главную карточку.)


- Подключение — **только** `python3 <кит>/tools/kit.py head <части>`: порядок
  тегов не вкус, тема первой, `dk-util.js` до всех `dk-*`.
- Разметку бери из `show <часть>` → «Пример», классы — из «Классы». Класса нет в
  описи — его нет в ките.
- Числа — `dkFmt`, строки из данных — `dkEsc`. Разметку в скриптах — узлами или
  через `dkEsc`.
- Раскладка — `dk-grid` и доли `dk-col--*`, каждый блок — в `dk-widget`.

## 4. Нет в ките — скажи

`find` ничего не нашёл, `charts` пишет «НЕТ В КИТЕ» — назови пробел человеку и
предложи замену из описи. **Не собирай самодельный блок молча** и не выдумывай
классы: проверка КЛАССЫ их поймает, а человек получит блок, который кит не держит.

## 5. Проверь и доведи

До первого показа исправь найденные проблемы смысла, композиции и поведения.
Для каждого вопроса из брифа найди видимый ответ или назови недостающие данные.
Не перекладывай выбор графиков, выравнивание и редактуру на человека.

По [checks.md](references/checks.md): проверки кита по странице, снимки
телефона 390 и десктопа 1280 в обеих темах, затем второй проход — **убрать
лишнее, а не добавить**. «Готово» — только когда проверки чистые; непроверенное
называй непроверенным.

## Неправильно → правильно

| ✗ | ✓ |
|---|---|
| теги `<link>/<script>` руками | `kit.py head …` |
| класс по памяти (`dk-col--three-quarters` — такого нет) | класс из `show layout` → «Классы» |
| фильтр в `<div>` на всю ширину | `dk-toolbar › dk-toolbar__group`, на телефоне строка пилюль |
| `style="color:#E0564F"` | смысл токеном: `--accent:var(--crit-ink)` |
| красный = бренд, зелёный = «кнопка ок» | красный/жёлтый/зелёный — только риск |
| две главные карточки на экране | одна `dk-hero`, остальное — плитки |
| график без подписи | `label` в описании графика; числа важны — таблица рядом |
| самодельный «было → стало» | `charts` → замена из описи или сказать о пробеле |
| просили график — собрал экран | собрал график; остальное — предложил словами |
| `el.innerHTML = dkIcon('x')` из данных, `append(dkIcon('x'))` | `el.append(dkIcon.el('x'))` — узел |

## 6. Визуал и задачи пользователя

Обязательные актуальные принципы: спокойный точный рабочий инструмент, нейтральные поверхности без теней (включая всплывающие слои), сильная типографика, полные названия объектов, семантический цвет данных/исключений. Не обрезай названия ради компактности. Порядок блоков определяй задачей; не добавляй карусель и KPI автоматически. Следуй [accessibility.md](references/accessibility.md) и DESIGN-UX-ACCESSIBILITY.md в корне кита.

## 7. Расширения и восстановление рабочего среза

Для drill-down, DOM-визуализаций, export/fullscreen и offline personalization
читай [extensions.md](references/extensions.md), затем `kit.py show/head`.
В JS смысл — `dkMeaning(name, 'text'/'fill')`; no-data — ровная нейтральная заливка плюс текст, без штриховки.
Старые API сохранены, update/destroy описаны в описи. Общий state связывает host,
а не автоматически превращает демонстрационные данные в production-срез.

## 8. Политика UI/UX

Перед сборкой читать UIUX.md и `.ai/project/uiux-policy.json`. Проверять основной
вопрос, контекст после фильтрации и возврата, обратную связь, состояния и
восстановление без повторного ввода. При ревью указывать применимые UI-ID,
сценарий и наблюдаемый результат; не считать наличие правила доказательством
соответствия. Кнопки брать из описи: приоритет по задаче, квадратный значок,
понятное имя, объяснимая недоступность. Не копировать размеры из статьи поверх
токенов и утверждённых правил пользователя.

Правила сочетаний читать в index.html#patterns и разделе «Когда использовать»
компонента: tooltip/видимый текст/детали, выбор значений, фильтрация, загрузка,
микровзаимодействия, движение и каркас. Для каждого интерактивного действия
определить триггер, результат, обратную связь, ошибку и повторное использование.
Не копировать промосайтные советы в мониторинг автоматически.

Полный процесс выбора и ревью: [uiux.md](references/uiux.md).
