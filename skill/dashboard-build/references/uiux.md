# От вопроса пользователя к проверенному экрану

Это порядок работы, а не второй список правил. Решения берутся из
[UIUX.md](../../../UIUX.md), [DECISIONS.md](../../../DECISIONS.md),
проектного реестра `.ai/project/uiux-policy.json` и описи компонентов.
Статьи помогают обосновать выбор; утверждённые решения пользователя имеют
приоритет. Наличие политики не означает, что конкретный экран проверен.

## 1. Вопрос и критерий ответа

До разметки записать одним предложением, кто пользуется экраном, какой ответ
ищет и что сделает после него. Перечислить необходимые данные, период,
актуальность, единицы и доступный источник. При отсутствии данных назвать
ограничение, не создавать правдоподобный ответ без основания.

Результат этапа — короткий сценарий и проверяемое условие успеха: например,
«дежурный видит, ухудшилась ли ситуация страны и какие округа требуют внимания».
«Добавить график» само по себе не объясняет задачу; при запросе одного графика
не расширять работу до нового экрана.

## 2. Информационная архитектура

Разложить необходимые сведения на основной ответ, объясняющие его данные и
детали объекта. Нарисовать путь «ответ → объект → действие → возврат», отметить
что нужно видеть одновременно. Сравниваемые сведения не разводятся по скрытым
вкладкам. Выбор представления следует задаче, а не наличию свободного места.

Если решения ещё нет, показать 2–3 конкретных варианта с их содержанием и
числом переходов. Полученный ответ записать в DECISIONS и подходящий reference;
уже утверждённое не спрашивать снова. Число кликов дополняется проверкой
понятности: скрытая обязательная информация или потеря контекста не считается
улучшением, даже если кнопок стало меньше.

Пример принятого решения для сводки: «Ситуация страны» — состав риска, четыре
KPI, динамика, округа и события; таблица работы в отдельной вкладке. Это пример
для данной задачи, а не обязательный шаблон каждого дашборда.

## 3. Компоненты и содержание

Для каждого блока назвать компонент из `kit.py list/show`, его роль и источник
данных. Прочитать «Когда использовать», состояния, API и связанные паттерны
в карточке компонента. Для отсутствующей возможности обозначить пробел до
реализации; не обещать поведение по похожему внешнему виду.

Результат этапа — карта «вопрос → данные → компонент → действие». Подставить
реальные длинные названия и числа до оценки размеров. Общие компоненты и
термины сопоставить с соседними экранами; новые отличия обосновать задачей.

## 4. Состояния и поведение

Для интерактивного блока записать триггер, изменение данных, обратную связь,
ошибку и повтор; отдельно отметить фокус и сохраняемый контекст. Выбрать
применимые состояния из реестра, без создания фиктивной загрузки у синхронного
примера. Связанные виджеты получают один срез; черновик фильтра отличается от
применённого выбора. При обновлении старые данные сохраняют прежнюю подпись.

Результат этапа — последовательность состояний с наблюдаемым итогом. Например:
«сменить период → показать обновление → получить согласованные показатели;
при ошибке сохранить фильтры и предложить повтор». Проверить повторный клик,
отмену и возврат; правила компонента должны описывать и эти переходы.

## 5. Проверка ответа и интерфейса

Сначала пройти целевой сценарий и путь восстановления. Записать, какие сведения
видны сразу, сколько действий потребовалось, сохранились ли период, фильтры,
объект, страница списка и фокус. Нельзя объявлять кратчайший путь доказанным
только по числу элементов или одному скриншоту.

Затем выполнить проверки из [checks.md](checks.md), просмотреть обе темы,
рабочее окно 1366×768, узкое окно и увеличенный текст. Для таблицы дополнительно
сравнить реальные строки и проверить заголовки, прокрутку, доступность действий.
Автоматические проверки не подменяют оценку понятности и не являются
исследованием с реальными участниками.

Результат ревью — сценарий, применимые UI-ID, подтверждённые решения пользователя,
наблюдения, результаты проверок и оставшиеся ограничения. Новое найденное
правило закрепляется в основном источнике, затем появляется в справочнике;
не оставлять его только в истории разговора.

## 6. Визуальная консистентность и справочник

Применять `design_guidance` из проектной политики и раздел TypeUI в UIUX.md.
Сохранять палитру, шрифт и токены кита. Иерархия — порядок, размер текста,
умеренная насыщенность и пространство; акцент — действие, состояние или данные.
Новый компонент наследует существующие размеры и поведение, а не получает
собственную тему. Для выбранного визуального варианта сравнить образец
с реализацией в одинаковом окне, затем проверить состояния и адаптацию.

Справочник начинать с выбора задачи и живого примера. Сравнивать варианты
на одинаковых данных; рядом объяснить назначение атомов, размеры, состояния
и клавиатурное управление. Код раскрывать после выбора компонента.
