💻Стек и библиотеки

Dashboard-kit — собственная библиотека интерфейса на HTML, CSS и JavaScript. HTML задаёт структуру, CSS — оформление и адаптацию, JavaScript — действия, состояние и обновление данных. React, Vue, Angular и Bootstrap в текущем ките не используются.

Нужно ли менять стек

Текущий кит остаётся на HTML, CSS и JavaScript: его можно использовать для самостоятельных дашбордов и подключать к приложению. React или Vue имеет смысл выбирать на уровне конкретного продукта, если этого требует его архитектура. Для встраивания нужно проверить адаптер, обновление данных и освобождение ресурсов — сама смена фреймворка эти задачи не решает.

Граница ответственности

Кит отвечает за интерфейс. Приложение подключает API, авторизацию, права доступа, расчёт метрик и сохранение данных. Экспорт и сохранённые виды используют доступные приложению данные; серверное хранение подключается отдельно.

Подключение и проверка

  1. Найти нужные части: python3 tools/kit.py list, затем python3 tools/kit.py show table chart.
  2. Получить теги подключения: python3 tools/kit.py head table chart. Тема подключается первой; dk-util — до остальных компонентов. Стили: primitives → semantic → components.
  3. Взять пример со страницы компонента и подключить свои данные. Строки экранировать через dkEsc, числа форматировать через dkFmt.
  4. Открыть через локальный сервер: python3 tools/preview.py --port 8771. Для карты и загрузки данных нужен HTTP.
  5. Запустить python3 tools/check.py --fast; полную проверку — python3 tools/check.py с Node.js 22+ и Chrome. Расширенный набор браузерных регрессий — python3 tools/test.py.

Что означает «без сборки»

Страница запускается из готовых HTML/CSS/JS-файлов. Python и Node.js нужны сопровождающим кит для генерации документации, проверки и обновления ресурсов; это не зависимости страницы в браузере.

Контракт и тиражирование

Целевой масштаб — десятки тысяч строк и больше, отдельные сайты и встраивание в ИИ-среду, анализ и рабочие действия. Сервер фильтрует и считает весь срез, браузер получает готовые агрегаты и одну страницу таблицы. Переключение страницы не меняет смысл KPI и графика.

Эталон «Работа служб» ↗ · Контракт данных и API · Учебный сервер · Версии и откат

Эталон использует вымышленные данные. Новый слой экспериментальный: до выпуска обязательны сквозная браузерная проверка, реальный источник и проверка прав и команд в приложении. Учебное поручение не создаёт рабочую задачу.

Как оценивать готовность

Проверяйте статус компонента, ограничения API и реальные сценарии: данные, клавиатуру, темы, размеры экрана, ошибку и восстановление. Статус «экспериментальный» требует отдельной проверки перед использованием. Текущие ограничения и технический долг описаны в REVIEW и HANDOFF.

📐Правила сборки

Начните с вопроса пользователя, выберите показатели и соберите экран из готовых частей. Данные, действия и состояния проверяются вместе.

Текущие принятые решения

Каждый ряд должен заполнять доступную ширину: для равноправных виджетов используйте dk-grid--balanced, для пяти КПЭ — dk-grid--five. Не резервируйте место под отсутствующий блок. Источники: README, DECISIONS, UX и доступность, REVIEW, HANDOFF. Поздние утверждённые решения заменяют исторические описания.

Порядок и KPI

  • Сначала статус и основные KPI, затем подробные графики, карта, списки и таблицы. Отдельная главная карточка только когда нужен состав или дополнительный контекст.
  • Основных KPI обычно пять (5 ± 2), максимум семь на обзорном экране. Самостоятельный KPI главной карточки входит в лимит. Не дублировать числа ради заполнения сетки.
  • КПЭ одного уровня имеют равные размеры. В семейной ипотеке шесть отдельных мини-виджетов одной полосой; при нехватке ширины полоса прокручивается, число и единица не разрываются. Не применять историческую сетку 2×2 к этой композиции.

Сетка и размеры окна

  • Заголовки называют показатель и группировку; период не дублируется. Графики с точными подписями значений обходятся без линий сетки. Соседние виджеты одного ряда имеют одинаковую высоту по самому высокому содержимому. Между рядами совпадают границы колонок и внутренние направляющие. Между виджетами ипотеки — 10px; внутренние поля задаёт --pad-widget, в текущем Graphite ипотеки это 18px на десктопе и 24px на телефоне.
  • Размер переключаемого виджета задаётся для текущего viewport: карта/список/плитки и месяц/неделя календаря сохраняют рамку. Resize пересчитывает базовый размер; данные прокручиваются внутри, текст не ужимается.
  • Проектировать от viewport и задачи; требование уместить конкретную сводку в 1366×768 не переносится на все дашборды. На телефоне ипотеки карта сохраняет читаемые плитки и сдвигается внутри ограниченного окна; список даёт полные названия.
  • На текущей сводке KPI 2×2 на телефоне, включая 320px. Статус и состав риска компактны; вкладки «Обзор / Работа / Аналитика» идут одной строкой. На планшете подробные виджеты располагаются друг под другом. Проверять 320–1920px, низкие окна и 200% текст.

Навигация и действия

  • Вкладки представлений сводки — под заголовком, перед статусом и содержимым.
  • Меню мониторинга — один плоский список без групп «Обзор» и «Работа». Радиус панели 12px; свёрнутая ширина 60px с обычным указателем.
  • Кнопки свёрнутого меню квадратные: 40×40px; на таче размеры растут вместе с токеном высоты.
  • Заголовок ипотеки слева, компактные фильтры и действия справа рядом с темой. Ширина/высота полей фиксированы для breakpoint; выбор и сброс не сдвигают соседей. Под условный сброс резервируется место. Длинное полное имя доступно в списке и aria-label.
  • Одна основная кнопка на задачу. Недоступное действие объясняется; в гостевой демонстрации выход отключён.

Данные и графики

  • Нет данных — ровная нейтральная заливка и текст; отсутствие отличается от нуля. Статусы читаются словами, а не только цветом. Для серии плана в ипотеке сохранена согласованная пунктирная линия сравнения.
  • Прогноз — обычная подпись без обводки и тени. Технические объяснения формы маркеров не выводятся в рабочий интерфейс.
  • Цвет не единственный носитель смысла: добавить слово, число или доступное описание. Шкала карты общая при фильтрации.
  • Период, единица измерения и база сравнения должны быть понятны. Тип графика выбирается по вопросу к данным.

Основная картина и детали

  • Экран сразу отвечает на основные вопросы. Выбор между вкладками, отдельными экранами и внутренней прокруткой зависит от задачи; единого обязательного шаблона нет.
  • Небольшой быстрый обзор региона — общая модалка: контекст, КПЭ, детализация, примечания, реальные действия. Много данных и длительная работа — отдельная страница с реальным маршрутом. Стандарт DASHBOARD-DETAIL-MODAL-001; вкладки только для самостоятельных представлений.
  • Сокращать клики до ответа на вопрос. Не прятать необходимые данные за переходами и не создавать цепочки вложенных модалок.
  • Между экранами сохранять одинаковые названия, статусы, общие действия, правила фильтрации, навигации и раскрытия деталей.
  • Примеры: обстоятельства выбранной заявки — детали; работа со всеми авариями — самостоятельный экран. Конкретный состав вкладок ещё не утверждён.

Текст и состояния

  • На дашбордах, в сборщиках и живых примерах не выводить лишние пояснения, инструкции по клику и постоянный блок методики. Подробности — по иконке информации или в документации.
  • Для привычных действий чаще выбирать кнопку-иконку с aria-label и подсказкой. Текст нужен, если иконка неоднозначна; ошибки и пустые состояния должны объяснять следующий шаг.
  • Полные названия, обычный регистр, конкретные действия. Убрать избыточные подписи вроде «в срезе 89 из 89» и инструкции по устройству интерфейса.
  • Число результатов появляется при активном поиске или фильтре. Пустой результат, отсутствие данных, загрузка и ошибка — разные состояния.
  • Для каждого компонента описать начальное состояние, выбор, недоступность, ошибки и обновление, если они применимы. Не обещать загрузку или сохранение в статическом примере, где их нет.

Доступность

  • У кнопки-значка обязательны aria-label и подсказка; декоративная иконка скрыта от скринридера.
  • Все действия доступны с клавиатуры; видимый фокус сохраняется. Диалог именуется, удерживает Tab, закрывается Escape и возвращает фокус.
  • На таче цели не меньше 44px. Проверять перенос текста и отсутствие горизонтального переполнения страницы при 200% тексте.
  • Автоматическая проверка AX tree не заменяет проверку настоящим скринридером и на физических устройствах.

Подключение и обновления

  • Статический HTML/CSS/JavaScript: не добавлять фреймворк или зависимости ради сборки экрана.
  • Токены: primitives → semantic → components. dk-theme первым, dk-util до остальных компонентов; зависимости берутся из описи.
  • Данные форматировать dkFmt, строки экранировать dkEsc. update и destroy использовать согласно API компонента, освобождая обработчики и подписки.
  • Быстрая проверка: python3 tools/check.py --fast. Полная: python3 tools/test.py с Chrome; пропуск браузера не является полной проверкой.
  • Изменения через PR, канал stable. Управляемый слой AI Ops не редактировать. Не публиковать и не сливать автоматически.

🧭UI/UX и эвристики

Основной ответ сразу; детали по задаче. Система берёт на себя проверку ввода, форматирование и сохранение контекста. Одинаковые действия сохраняют названия и поведение между экранами.

Политика: правила, кнопки, состояния и способы проверки. Ниже — критерии проверки интерфейса. Подробный технический реестр предназначен для ревью реализации.

🧩Как выбирать и сочетать компоненты

Начните с задачи: что человек выбирает, сравнивает или уточняет. В каждом разделе — подходящие компоненты, частые ошибки и способ проверить результат.

Подсказки
  • Только короткое дополнительное пояснение; необходимые инструкции остаются видимыми.
  • Появление по фокусу, наведению или явному касанию; Escape закрывает подсказку, фокус остаётся на кнопке.
  • Без ссылок и действий внутри. Не перекрывать источник пояснения; длинный текст — в деталях.

Избегать: Правило расчёта доступно только при наведении.

Выбирать: Порог виден рядом с показателем, подсказка поясняет дополнительный термин.

Проверка: Проверить край окна, клавиатуру, касание и перевод указателя на подсказку.

Окна и детали
  • Модалка открывается для локальной задачи, требующей внимания; обычное сообщение не блокирует экран.

Проверка: Пройти открытие, закрытие, отмену, ошибку и возврат к прежнему срезу.

Данные и состояние дашборда

Контракт данных и единый согласованный срез: серверные агрегаты, страница таблицы, загрузка, ошибка, повтор и защита от устаревших ответов.

Статус: экспериментальный

Когда использовать

  • Связанные KPI, график и таблица используют один источник и фильтры.
  • Большие данные: фильтрация, агрегаты и пагинация выполняются на сервере.

Правила и поведение

  • schemaVersion=1. null означает отсутствие данных; ноль — измеренное значение.
  • В server-режиме KPI и series относятся ко всему срезу, rows — к текущей странице.
  • Новый запрос вытесняет предыдущий, timeout и destroy освобождают ожидание даже при игнорировании AbortSignal.
  • Загрузка и ошибка не показывают данные предыдущего среза под новыми фильтрами.
  • Команды, авторизация и права — ответственность приложения; сервер эталона содержит только учебные данные.

Раскладка

Сетка на 12 колонок с долями, раскладка «основное плюс боковая колонка», виджет — общая коробка для любого блока, шапка страницы, вложенная зона.

Статус: стабильный

Когда использовать

  • Любой дашборд: блоки ставятся в dk-grid долями dk-col--*, каждый блок — dk-widget.

Правила и поведение

  • Равная высота соседних карточек — dk-grid--equal; ряд по самому высокому содержимому, без внутренней прокрутки.
  • Ширина — долей (--quarter, --third, --half, --two-thirds, --full), а не числом колонок.
  • Не больше трёх-четырёх подробных виджетов в ряду; сверху вниз — от общего к частному.
  • dk-grid--five: пять KPI на широком экране, до трёх на планшете, до двух на телефоне; каждый фактический ряд заполняет ширину, включая неполный последний.
  • dk-grid--balanced: равноправные виджеты распределяются по доступной ширине, последний ряд не оставляет пустых колонок. Не резервировать места под отсутствующие или скрытые блоки.
  • dk-grid--overview-panels: только для трёх панелей; для другого состава брать balanced. Панели 1.45:1.05:1; на планшете две колонки с первой панелью во всю строку, на телефоне одна.
  • Размер S — четверть: число, подпись, тренд, спарклайн. График с осями в четверть не ставится.
  • Фильтры — одной строкой над содержимым, а не внутри виджетов.

💬Как работать с ИИ

Один сценарий для менеджера, аналитика, дизайнера и разработчика: вы задаёте цель и уточняете результат, помощник использует кит для реализации.

Что передать

Достаточно описать нужный результат и предоставить доступные данные. Если важны аудитория, период, определения показателей или ограничения, добавьте их. Помощник уточнит то, без чего нельзя корректно продолжить.

Что делает помощник

Изучает данные и правила кита, предлагает понятную структуру экрана, выбирает компоненты, подключает расчёты и взаимодействия. Проверяет результат и сообщает о недостающих данных, доступах и непроверенных сценариях.

Как принять результат

  • Дашборд отвечает на ваш исходный вопрос.
  • Показатели понятны и сходятся с источником; примеры не выданы за реальные данные.
  • Фильтры обновляют весь связанный срез, а детализация помогает объяснить результат.
  • Помощник показал рабочий экран и назвал ограничения проверки.

Когда нужен справочник

Компоненты, API и правила доступны для помощника и для тех, кто хочет углубиться в детали. Читать их перед постановкой задачи не обязательно.
